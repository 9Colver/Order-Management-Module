# 1. MODULE DESCRIPTION

The Order Management Module is responsible for managing the shopping carts, cart items, customer orders, order items, order status history, and prescription submissions of the MedEx system.

This module connects customers, pharmacies, products, inventory, payments, and deliveries. Information owned by other modules is accessed through database relationships and is never duplicated.

The module uses Supabase PostgreSQL for storing and managing records and a private Supabase Storage bucket for prescription files.

# 2. MODULE OBJECTIVES

The objectives of the Order Management Module are:

1. To store and manage the active shopping cart of each resident.
2. To store the products and quantities added to a cart.
3. To record submitted orders, including delivery address and recipient snapshots.
4. To preserve historical product and price information for every order.
5. To record every order status change.
6. To store prescription submission details and file references.
7. To coordinate stock reduction and restoration with the Inventory module.
8. To maintain the integrity of order records and prevent duplicate orders.

## 3.1 CARTS TABLE

Description:

Stores the active shopping cart of each customer. A cart belongs to one pharmacy at a time. The cart total is not stored; it is calculated from cart_items and product prices.

| Column Name | Data Type | Constraint |
|---|---|---|
| cart_id | UUID | Primary Key, DEFAULT gen_random_uuid() |
| user_id | UUID | Foreign Key, NOT NULL, UNIQUE |
| merchant_id | UUID | Foreign Key, NULL |
| created_at | TIMESTAMPTZ | DEFAULT NOW() |
| updated_at | TIMESTAMPTZ | DEFAULT NOW() |

Primary Key: cart_id

Foreign Keys:
- user_id references users(user_id).
- merchant_id references merchant_profiles(merchant_id).

Note: user_id is unique, so each resident has only one active cart.

## 3.2 CART_ITEMS TABLE

Description:

Stores the products and quantities added to a cart. A product appears once per cart; its quantity is updated instead of inserting a duplicate.

| Column Name | Data Type | Constraint |
|---|---|---|
| cart_id | UUID | Primary Key (composite), Foreign Key |
| product_id | UUID | Primary Key (composite), Foreign Key |
| quantity | INTEGER | NOT NULL, CHECK quantity > 0 |
| added_at | TIMESTAMPTZ | DEFAULT NOW() |
| updated_at | TIMESTAMPTZ | DEFAULT NOW() |

Primary Key: composite (cart_id, product_id)

Foreign Keys:
- cart_id references carts(cart_id) ON DELETE CASCADE.
- product_id references products(product_id).

## 3.3 ORDERS TABLE

Description:

Stores the main order information after checkout. The delivery address and recipient details are snapshots taken at checkout.

| Column Name | Data Type | Constraint |
|---|---|---|
| order_id | UUID | Primary Key, DEFAULT gen_random_uuid() |
| order_code | VARCHAR(30) | UNIQUE, NOT NULL, generated by the database |
| idempotency_key | VARCHAR(64) | UNIQUE, NOT NULL |
| user_id | UUID | Foreign Key, NOT NULL |
| merchant_id | UUID | Foreign Key, NOT NULL |
| address_id | UUID | Foreign Key, NULL |
| alert_id | UUID | Foreign Key, NULL |
| recipient_name | VARCHAR(100) | NOT NULL |
| recipient_phone | VARCHAR(20) | NOT NULL |
| delivery_address | TEXT | NOT NULL |
| delivery_landmark | VARCHAR(255) | NULL |
| delivery_note | TEXT | NULL |
| subtotal | NUMERIC(10,2) | NOT NULL, CHECK >= 0 |
| delivery_fee | NUMERIC(10,2) | NOT NULL, CHECK >= 0 |
| total_amount | NUMERIC(10,2) | NOT NULL, CHECK >= 0 |
| payment_method | VARCHAR(20) | NOT NULL, DEFAULT 'cod', CHECK = 'cod' |
| status | VARCHAR(40) | NOT NULL, CHECK in allowed values |
| cancel_reason | TEXT | NULL |
| cancelled_by | UUID | Foreign Key, NULL |
| cancelled_at | TIMESTAMPTZ | NULL |
| placed_at | TIMESTAMPTZ | NULL |
| completed_at | TIMESTAMPTZ | NULL |
| created_at | TIMESTAMPTZ | DEFAULT NOW() |
| updated_at | TIMESTAMPTZ | DEFAULT NOW() |

Primary Key: order_id

Foreign Keys:
- user_id references users(user_id).
- merchant_id references merchant_profiles(merchant_id).
- address_id references addresses(address_id).
- alert_id references emergency_alerts(alert_id).
- cancelled_by references users(user_id).

Table Check: total_amount = subtotal + delivery_fee.

Notes:
- order_code is a human-readable reference, e.g. OR-261119-00001.
- idempotency_key prevents duplicate orders on retry.
- address_id is the original saved address, when available.
- alert_id is the verified alert used for emergency-priced items.
- delivery_fee is PHP 30.00, copied from configuration.
- subtotal is the sum of the order item line totals.

Allowed Statuses: awaiting_prescription_review, pending, placed, preparing, ready_for_pickup, out_for_delivery, delivered, cancelled.

Note: "On hold" is not a status. A rejected prescription keeps the order in awaiting_prescription_review, and the latest prescriptions row is rejected.

## 3.4 ORDER_ITEMS TABLE

Description:

Stores each product in an order, with historical product details and price snapshots.

| Column Name | Data Type | Constraint |
|---|---|---|
| order_item_id | UUID | Primary Key, DEFAULT gen_random_uuid() |
| order_id | UUID | Foreign Key, NOT NULL |
| product_id | UUID | Foreign Key, NULL |
| product_name | VARCHAR(150) | NOT NULL |
| generic_name | VARCHAR(150) | NOT NULL |
| brand_name | VARCHAR(150) | NOT NULL |
| strength | VARCHAR(150) | NOT NULL |
| dosage_form | VARCHAR(50) | NOT NULL |
| unit | VARCHAR(50) | NOT NULL |
| unit_price | NUMERIC(10,2) | NOT NULL, CHECK >= 0 |
| quantity | INTEGER | NOT NULL, CHECK quantity > 0 |
| line_total | NUMERIC(10,2) | NOT NULL, CHECK >= 0 |

Notes:

- Every item must belong to the same merchant as the order (validated in the backend).

# 7. BUSINESS AND INTEGRITY RULES

## 7.1 Database Integrity Rules

1. A resident must have a valid user record.
2. A cart must belong to a valid resident and pharmacy.
3. Only one active cart per resident is allowed (carts.user_id is unique).
4. Cart item quantity must be greater than zero.
5. Order amounts cannot be negative, and total_amount = subtotal + delivery_fee.
6. Order item quantities must be greater than zero.
7. Order item unit prices and line totals cannot be negative, and line_total = unit_price × quantity.
8. Order records must preserve historical information.
9. Order status changes must be recorded in order_status_history.
10. Prescription file references must point to files stored in Supabase Storage.
11. A rejected prescription must have a rejection reason.
12. Duplicate orders are prevented by the unique idempotency_key.
13. Transactions must be used when creating orders and reducing or restoring stock.

## 7.2 Historical Order Information

Order records preserve the information applicable when the customer submitted the order:

- Product name snapshots.
- Medicine details and unit snapshots.
- Unit price snapshots.
- Delivery address snapshots.
- Recipient information snapshots.

Changes to a customer's address or a pharmacy's product information must not rewrite historical order details. order_items.unit_price must be used for historical prices, never the current product price.

## 7.3 Inventory Integration

M4 coordinates with M3 (decided 2026-11-17, C10):

- inventory.stock_quantity is reduced in the same transaction that creates the order (through Inventory::reserve).
- Orders must not exceed stock_quantity.
- Stock is restored when an order is cancelled, times out, or its delivery fails.
- There is no reserved_quantity and no separate deduction on completion.
- Database transactions are used to prevent inconsistent stock records.

## 7.4 Emergency Alert Rule (C9)

orders.alert_id is nullable. For emergency-priced items:

- The alert must belong to the same resident.
- The alert must be verified.
- The order must be created before access_expires_at.
- The per-alert purchase limit is the sum of order_items.quantity for that product across the alert's non-cancelled orders.

These checks are enforced in the backend.

## 7.5 Payment and Delivery Integration

- Each order has an associated payment record (M5).
- MEDEX supports COD only (C2). M4 must not implement online payment gateway fields or callbacks.
- Delivery information is maintained by M6.

## 7.6 Timers

| Timer | Action |
|---|---|
| 4 hours | Reminder |
| 12 hours | Admin notice |
| 24 hours | Auto-cancel (prescription hold and closed-pharmacy pending) |

# 8. DATABASE SECURITY

The module follows security practices to protect order and prescription information.

1. Prescription files are stored in a private Supabase Storage bucket; only the file path is saved in the database.
2. Duplicate orders are prevented through the unique idempotency_key.
3. Transactions are used when creating orders and when reducing or restoring stock.
4. Business rules that cannot be enforced by constraints (merchant matching, emergency alert checks) are enforced in the backend.
5. Row Level Security (RLS) should be enabled on tables containing private customer information.
6. Users should only access records they are authorized to view or modify.
7. Database permissions must be properly configured.

# 9. CONCLUSION

The Order Management Module provides the foundation for managing carts, orders, order history, and prescriptions in the MedEx system.

Through its six database tables, the module organizes shopping carts, submitted orders, historical item and price snapshots, status changes, and prescription reviews.

Its relationships allow it to work with the User, Emergency Alert, Store, Payment, and Delivery modules while maintaining proper database organization and consistent historical records.
